────────────────────────────────────────────────────────────────────────────────
VARIABLE DEFINITIONS
────────────────────────────────────────────────────────────────────────────────

  n   = number of incidents (user-plotted, app max 300)
  p   = number of patrols (user-selected, app max 100; also bounded by C)
  C   = valid candidates: intersection nodes inside the convex hull (up to ~914)
  V   = road graph nodes (~3,613 for Commonwealth)
  E   = road graph edges (~8,000–10,000 for Commonwealth)
  m   = deduplicated crime nodes entering zone assignment (≤ n, app max 300)
  k   = crime nodes per zone (hard cap: maxCrimeNodesPerZone = 10 by default;
        backtracking used for k ≤ 12, nearest-neighbor for k > 12)
  h   = hull vertex count (≤ n, typically 3–20 in practice)
  N   = total road nodes = ~3,613 (used in ray cast pre-filter)
  R   = max restarts = config.hillClimbing.restarts × p = 10p (default)
        capped early by adaptive convergence (last 3 restarts within 0.1%)
  I   = max iterations per restart = 500 (config constant)
  min_R = minimum restarts = max(5, p) (always runs at least this many)

  App-level bounds (hardcoded limits or config defaults):
    n   ≤ 300
    p   ≤ 100  (and ≤ C — capped to validCandidates.length if exceeded)
    C   ≤ ~914 (intersection nodes inside hull; shrinks with smaller hull area)
    k   ≤ 10   (zone cap) or ≤ 12 (backtracking threshold)
    I   = 500  (config, treated as constant in complexity expressions)
    R   = 10p  (scales with patrol count, not incident count)


────────────────────────────────────────────────────────────────────────────────
STAGE 1 — BRUTE FORCE CONVEX HULL  (convexHull.js)
────────────────────────────────────────────────────────────────────────────────

Algorithm steps:
  1. Incremental update check (if previousHull exists): O(n_new × h) ray casts
  2. Outlier detection: O(n) — centroid + per-point haversine distance
  3. Collinearity check: O(n) — single pass, early exit on first non-collinear point
  4. Brute force hull: O(n³) — for each ordered pair (i,j), test all other k
     Inner loop exits early on first d < 0 (non-CCW point found)
  5. Edge ordering: O(h²) — chain-link traversal of valid directed edges; h ≤ n
  6. Shoelace area: O(h)
  7. Winding normalization: O(h)
  8. Ray cast pre-filter: O(N × h) — each of ~3,613 road nodes tested against hull
     Bounding box pre-filter eliminates most nodes before full ray cast
  9. Valid candidates cache: O(h) comparison — skips ray cast entirely on cache hit

BEST CASE: O(n)
  Trigger: Incremental update path — incident set is identical to previous run
  (detected at hillClimbing.js line 186–196: no new points, no removed points)
  Returns cached hull immediately. Only cost is O(n) comparison of current vs
  previous incident arrays.

  Best case (fresh run, no previous hull): O(n²)
  Trigger: Inner loop of brute force hull exits after 1 check for most edges —
  the first point k tested disqualifies each non-hull directed edge (i,j) immediately.
  Hull vertex count h is small (O(log n) expected for uniform distributions),
  so edge ordering and ray cast pre-filter are fast.

AVERAGE CASE: O(n³)
  The brute force triple loop cannot be optimized without a fundamentally different
  algorithm. For a typical random point set, most edges require checking several
  points before finding a disqualifying one, but the asymptotic bound does not
  improve below O(n³). The ray cast pre-filter O(N × h) is dominated by O(n³)
  since n³ > N × n when n > sqrt(N) ≈ 60, which is true for most real inputs.

WORST CASE: O(n³)
  Trigger: All n incidents lie on the convex hull (e.g., points on a circle).
  For every directed edge (i,j), the inner loop must scan all n-2 remaining points
  to confirm none lie to the right — no early exit.
  n³ = 300³ = 27,000,000 operations at max input.

  Ray cast pre-filter adds O(N × h) = O(3,613 × n) in worst case (no bbox
  rejections, hull has n vertices). This is dominated by O(n³) for n > 60.

Note: The incremental update optimization (V2) makes repeated recalculations
significantly cheaper. Only a full recompute (first run or new points outside
the hull) incurs O(n³).


────────────────────────────────────────────────────────────────────────────────
STAGE 2 — HILL CLIMBING PATROL PLACEMENT  (hillClimbing.js)
────────────────────────────────────────────────────────────────────────────────

Two separate phases with independent complexity:

──── Phase A: Road Distance Matrix Pre-computation (buildRoadDistMatrix) ────

  Runs Dijkstra once from every valid candidate node C.
  Stores all pairwise road distances: matrix[src][dst] for all C² pairs.
  Used by Hill Climbing for O(1) distance lookups.

  BEST CASE:  O(C × (V+E) log V)   — no shortcut; always runs in full
  AVERAGE:    O(C × (V+E) log V)   — same; no caching at this phase
  WORST CASE: O(C × (V+E) log V)   — same

  With C = 914, V+E ≈ 12,000, log V ≈ 12:
    Approx. 914 × 12,000 × 12 ≈ 131,616,000 operations

──── Phase B: Hill Climbing Restart Loop ────

Per-iteration cost breakdown (asynchronous mode, default):
  For each patrol i (p patrols per iteration, shuffled):
    findNeighbors:        O(C)    — scan candidates, O(1) roadDistMatrix lookup each
    minPairwiseExcluding: O(p²)   — all pairs not involving patrol i
    Best-neighbor scan:   O(C×p)  — for each ≤C neighbors, O(p) distance to others
  Per patrol total:       O(C × p)
  Per iteration (p patrols): O(C × p²)
  Radius expansion (when no neighbors found): rare, adds 1 extra iteration

Restart budget:
  Max restarts R = config.hillClimbing.restarts × p = 10p
  Min restarts   = max(5, p)
  Adaptive convergence stops early when last 3 restarts are within 0.1%

BEST CASE: O(p² × C)
  Trigger: First random placement is already optimal — anyPatrolMoved = false
  after 1 iteration in every restart. Only minimum restarts (max(5,p)) are run.
  Cost: max(5,p) restarts × 1 iteration × O(p × C) per iteration = O(p² × C)

AVERAGE CASE: O(R_avg × I_avg × p² × C)
  In practice, adaptive convergence stops after ~5–15 restarts (R_avg << 10p).
  Iterations typically converge in 20–100 steps (I_avg << 500).
  Effective cost roughly O(p × 10 × 50 × p² × C) = O(500 × p³ × C)
  with much smaller real constants than worst case.

WORST CASE: O(p³ × I × C)
  Trigger: All 10p restarts run to the 500-iteration cap with no convergence.
  No adaptive early stop fires (results vary by > 0.1% every 3 restarts).
  Cost: R × I × p² × C = 10p × 500 × p² × C = 5,000 × p³ × C

  With p = 100, I = 500, C = 914:
    5,000 × 100³ × 914 ≈ 4,570,000,000,000 (4.57 trillion) operations

  This is the dominant term for the entire system.

Note on synchronous mode (CONFIG.hillClimbing.synchronousMode = true):
  Phase 1 (compute proposals) and Phase 2 (apply moves) each cost O(p × C) and
  O(p) respectively per iteration. Same asymptotic complexity as async mode.


────────────────────────────────────────────────────────────────────────────────
DIJKSTRA  (dijkstra.js — used by Stages 2, 3, 4)
────────────────────────────────────────────────────────────────────────────────

Implementation: single-source shortest path, binary min-heap with position map.
  - Position map gives O(1) index lookup → O(log V) decreaseKey (not O(n) scan)
  - Traverses the FULL road graph (all V nodes, all E edges)
  - Early exit: if extractMin() returns Infinity, rest of graph is disconnected

Shared cache (dijkstraCache): keyed by sourceId. One run stores distances and
parents to all reachable nodes. Any subsequent query for the same source is O(1).
Cache is initialized fresh per pipeline run and shared across Stages 3 and 4.

BEST CASE: O(1)
  Trigger: dijkstraCache[sourceId] already populated (cache hit).
  Returns stored {distances, parents} immediately.
  Happens frequently in Stage 4 because Stage 3 pre-computes many sources.

AVERAGE CASE: O((V+E) log V)
  Fresh run on a well-connected graph. Heap processes most nodes.
  With V ≈ 3,613, E ≈ 10,000, log V ≈ 12:
    ≈ 13,613 × 12 ≈ 163,356 operations per fresh Dijkstra call

WORST CASE: O((V+E) log V)
  Same as average — no structural difference for worst-case input.
  The early-exit optimization (break on Infinity dequeue) helps on disconnected
  graphs but does not change the asymptotic bound.

Path reconstruction (reconstructPath): O(path_length) — follows parent pointers.
normalizedCacheKey: O(1) — numeric parse + compare + string join.


────────────────────────────────────────────────────────────────────────────────
STAGE 3 — ZONE ASSIGNMENT  (zoneAssignment.js)
────────────────────────────────────────────────────────────────────────────────

Algorithm steps:
  1. Hull diameter: O(h²) — all hull vertex pairs; h typically 3–20, negligible
  2. Snapping: O(m × C) worst — bbox pre-filter then haversine per candidate;
     radius expands by 50% on miss, capped at hull diameter
  3. Deduplication: O(m) — Map lookup per snapped node
  4. Dijkstra pre-computation: O(m_unique × (V+E) log V) — one run per unique
     snapped node ID; hits dijkstraCache for nodes already computed in Stage 2
  5. Initial assignment: O(m × p) — for each crime node, check all p patrol distances
  6. Zero-distance detection: O(m × p) — post-assignment node ID comparison
  7. Light rebalancing: max 10 iterations; each scans the largest zone O(m_largest)
     → O(10 × m) total
  8. Strong rebalancing (opt-in): O(m²) worst — scans overloaded × underloaded pairs
  9. Zone cap sort: O(m_zone × log m_zone) per zone; total O(m log m)
 10. Zone classification: O(p)

BEST CASE: O(m × p)
  Trigger: All m unique snapped node IDs already in dijkstraCache (100% cache hits
  from Stage 2's buildRoadDistMatrix). No new Dijkstra runs needed.
  Cost is just the initial assignment loop: O(m × p).
  Snapping is fast when all crime nodes are near candidates: O(m) at minimum.

AVERAGE CASE: O(m_miss × (V+E) log V + m × p)
  Some crime nodes' snapped positions were not valid candidates in Stage 2
  (they snapped to non-intersection nodes not in roadDistMatrix) → cache misses.
  m_miss is typically small. Most of the m Dijkstra queries are cache hits.

WORST CASE: O(m × (V+E) log V)
  Trigger: No cache hits — all snapped node IDs are different from the C
  valid candidates computed in Stage 2 (e.g., snapping to non-intersection nodes).
  With m = 300, V+E ≈ 12,000, log V ≈ 12:
    300 × 12,000 × 12 ≈ 43,200,000 operations (dominated by Hill Climbing)

  Snapping worst case O(m × C): all crime nodes require full radius expansion
  to hull diameter, scanning all C candidates without bbox rejection.


────────────────────────────────────────────────────────────────────────────────
STAGE 4 — TSP + ROAD-FOLLOWING ROUTES  (tsp.js)
────────────────────────────────────────────────────────────────────────────────

Algorithm steps per patrol zone of size k:
  1. Build distance matrix: k+1 Dijkstra calls (patrol start + k crime nodes)
     Many are cache hits from Stage 3 → effective cost much lower than O(k×(V+E)log V)
  2. Remove unreachable crime nodes: O(k) — check D[patrol][crime] == Infinity
  3. TSP:
       k = 2:        O(1) shortcut — both orderings have identical circuit distance
       3 ≤ k ≤ 12:  backtracking with pruning — discard branch if accumulated >= best
       k > 12:       nearest-neighbor heuristic — O(k²) greedy
  4. Sequence adjustment: O(k² × path_length) — move intermediately-traversed
     crime nodes to point of natural traversal; bounded, not dominant
  5. Path segment build: O(k × path_length) — reconstruct road coordinates per leg
  6. Overlap detection: O(total_edges) across all patrols

──── Backtracking TSP complexity ────

  BEST CASE per zone: O(k²)
    First complete path explored is optimal. Every subsequent branch is pruned
    at the first step (accumulated >= bestCircuit immediately).
    Cost: O(k) to reach leaf + O(k) prune checks for remaining k! - 1 branches
    ≈ O(k²) total with perfect pruning.

  AVERAGE CASE per zone: O(k² × 2^k)
    Empirically observed for random distance matrices with pruning. At k=10:
    O(100 × 1024) ≈ 102,400 operations per zone (heavily pruned in practice;
    trace panel shows 70–90% of branches pruned).

  WORST CASE per zone: O(k!)
    No pruning fires — distance matrix has no structure allowing early cutoff.
    k ≤ 12 (backtracking threshold): 12! = 479,001,600 operations.
    k ≤ 10 (zone cap default):       10! =   3,628,800 operations.
    Since k is bounded by a constant, O(k!) is a bounded constant per zone.

Across p patrol zones:

  BEST CASE: O(p + p × k × (V+E) log V)
    If all Dijkstra calls are cache hits from Stage 3: O(1) each.
    TSP with perfect pruning: O(p × k²).
    Total: O(p × k²) ≈ O(p) since k ≤ 12 constant.

  AVERAGE CASE: O(p × k² × 2^k + p_miss × k × (V+E) log V)
    where p_miss = patrol zones with Dijkstra cache misses.

  WORST CASE: O(p × k! + p × k × (V+E) log V)
    All k! backtracks per zone + all Dijkstra calls are cache misses.
    With k bounded by constant (10 or 12): O(p × const + p × k × (V+E) log V)
    = O(p × k × (V+E) log V) asymptotically when treating k as variable,
      or O(p) when treating k as a bounded constant.

  With p = 100, k = 12, V+E = 12,000, log V = 12:
    TSP:      100 × 12! ≈ 47,900,160,000 (47.9 billion) operations
    Dijkstra: 100 × 12 × 12,000 × 12 ≈ 172,800,000 operations

────────────────────────────────────────────────────────────────────────────────
WORST CASE — ENTIRE SYSTEM
────────────────────────────────────────────────────────────────────────────────

All stages run sequentially. Total worst case = sum of all stage worst cases.

  Stage 1:  O(n³)
  Stage 2A: O(C × (V+E) × log V)          [road distance matrix]
  Stage 2B: O(p³ × I × C)                 [Hill Climbing]
  Stage 3:  O(m × (V+E) × log V)          [zone assignment Dijkstra]
  Stage 4:  O(p × k! + p × k × (V+E) × log V)  [TSP + path reconstruction]

Combined:
  T_total = O( n³  +  C(V+E)log V  +  p³·I·C  +  m(V+E)log V  +  p·k! )

Simplified (dropping dominated terms):

  ┌─────────────────────────────────────────────────────────────┐
  │  SYSTEM WORST CASE:  O(p³ · I · C)                         │
  │                   =  O(p³ · C)  treating I = 500 as const  │
  └─────────────────────────────────────────────────────────────┘

  Hill Climbing (Stage 2B) completely dominates all other stages.

──── Numerical comparison at maximum input bounds ────

  Stage               Expression                           Approx. Operations
  ─────────────────────────────────────────────────────────────────────────────
  Stage 1 Hull        n³ = 300³                            27,000,000
  Stage 2 Matrix      C(V+E)log V = 914 × 12,000 × 12     131,616,000
  Stage 3 Dijkstra    m(V+E)log V = 300 × 12,000 × 12      43,200,000
  Stage 4 TSP         p × k! = 100 × 479,001,600           47,900,160,000
  Stage 2 Hill Climb  p³·I·C = 100³ × 500 × 914        4,570,000,000,000   ← DOMINANT
  ─────────────────────────────────────────────────────────────────────────────

  Dominance order: Hill Climbing >> TSP >> Road Matrix >> Zone Dijkstra >> Hull

──── Why other stages are absorbed ────

  Stage 1 O(n³):         27M vs 4.57T — 5 orders of magnitude smaller
  Stage 2 Matrix O(C·…): 131M vs 4.57T — absorbed into Hill Climbing constant
  Stage 3 O(m·…):        43M vs 4.57T — absorbed
  Stage 4 O(p·k!):       47.9B vs 4.57T — 2 orders of magnitude smaller

  Since k is a bounded constant (cap = 10, threshold = 12), O(p·k!) = O(p),
  which is also dominated.

──── Practical note ────

  The O(p³·I·C) bound is the theoretical ceiling under adversarial conditions
  (every restart runs all 500 iterations, no convergence ever detected).

  In practice:
    - Adaptive convergence stops after 5–15 restarts (not 10p)
    - Inner loops exit early when the first improving neighbor is found
    - Most Dijkstra calls in Stages 3 and 4 are O(1) cache hits
    - The observed pipeline runtime for 30 incidents, p=10 is under 1 second

  The practical average-case behavior is closer to O(p · C) than O(p³ · C).
